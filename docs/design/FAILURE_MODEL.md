# Mostra failure, recovery and concurrency model

**Status:** Settled v1 behavior (C03-A). It covers every case STANDARDS requires: invalid or missing configuration, partial persistence, timeouts, cancellation, process crash, duplicate execution, stale versions, concurrent tabs and clients, host unavailability and unsupported platforms. Each row names the observable behavior and the owner. The evidence matrix maps rows to tests.

## 1. Rules that every case follows

1. **Durable before acknowledged.** A mutation, submission, run start, push or publish is acknowledged only after its ledger transaction commits (`synchronous=FULL`, D71). A client that saw a success can rely on it after any crash.
2. **One writer.** Only the supervisor writes the ledger. Children send requests over IPC and never hold ledger state. Concurrency is resolved inside one transaction, never with in-memory locks spread across processes.
3. **Idempotent by stable IDs.** Every retryable request carries a stable ID (mutation ID, request ID, submission ID, delivery ID, run key). Replays return the recorded result.
4. **Fail closed** where pretending would corrupt state, lose input, leak data or mislead (STANDARDS). Typical cases: a submit that can't be made durable, a token check that can't be evaluated, a ledger that can't be opened, a version that can't be resolved.
5. **Say what happened and what to do.** Every failure surfaces as a diagnostic with a stable code and a hint (INTERFACES §13): to the agent as JSON, to the viewer as plain words in the shell.

## 2. Processes

| Failure | Behavior |
|---|---|
| Two supervisors start for one home | Ownership is the ledger's exclusive SQLite lock, taken before the socket (D81). The first starter to take it owns the home; the lock fails at once for the others. A daemon starter that loses reads `instance.json` and attaches to the socket recorded there, waiting a bounded time while the owner finishes starting. Only when that socket can't be reached does it fail with `MOSTRA_HOME_LOCKED`, naming the owner's PID and how to restart it. `mostra host` never attaches: it gets `MOSTRA_HOME_LOCKED` naming the owner's PID (prototype: 3 × 16 racers, one winner each) |
| Stale socket after a crash | The operating system released the dead supervisor's lock. The next starter takes it, unlinks the leftover socket file and binds a new one. No takeover mutex is needed, because only the lock holder touches the socket. A stale `instance.json` (its PID and start time match no live process) is replaced |
| Socket file removed while the supervisor runs (for example a Linux logout removing `$XDG_RUNTIME_DIR`) | The supervisor checks its socket at least every 10 s and re-creates it. Until then, starters find the owner through `instance.json`, and no second supervisor can start because the lock is held |
| Supervisor crashes or is killed | Children notice the IPC disconnect, signal their own process group and exit. Process groups make sure grandchildren (demo servers, PTY programs) die too; a child that runs programs in their own sessions (the PTY host) registers them with the supervisor. On the next start the supervisor reaps every recorded `child` row: when the recorded leader's PID and start time still match, or the leader is gone and the machine hasn't rebooted, it signals the group's members that started no earlier than the leader (SIGTERM, then SIGKILL). A PID now held by an unrelated process is left alone. Committed state is intact, and in-flight requests were unacknowledged, so clients retry them by ID |
| On Windows: two supervisors start for one home (D150) | The same ledger lock decides: SQLite's exclusive lock is a Windows file lock, released when the process dies. The owner's control endpoint is a named pipe the helper serves, `\\.\pipe\mostra-<home hash>-<random>`, fresh on every bind and recorded in `instance.json`; losers attach to it as on POSIX (16 racers, one winner, on x64 and arm64) |
| On Windows: the supervisor crashes or is killed (D150) | Each child's gate holds the child's Job Object with kill-on-close and watches its lifeline: when the supervisor dies, the job ends the child and every descendant at once. The pipe's helper ends too, so the pipe disappears. A gate that missed its lifeline (hung) leaves its family running; the next start reaps each recorded child by ending its job, opened by its name, and the child when its PID and creation time still match. A process that only shares a recorded PID is left alone |
| On Windows: the pipe's helper stops while the supervisor runs | The supervisor notices within 10 s, binds a new pipe under a new name and rewrites `instance.json`; until then starters can't attach, and no second supervisor can start because the lock is held |
| On Windows: stopping an instance | Windows has no signals between processes: `mostra/shutdown` (what `mostra daemon stop` sends), the host closing stdio, or Ctrl+C or Ctrl+Break at the console stop it cleanly (D87). A child stops over its own channel where it has one, then by its lifeline, which ends its job |
| On Windows: a worker crashes, runs out of memory or hangs (D151) | As on POSIX: out of memory by Node.js's message or exit 134, which Windows gives too; a hang by the watchdog, which stops the worker's job; a native crash by its exit status, named in hexadecimal (`0xC0000005`). The worker's gate's job ends whatever server code started (D150) |
| On Windows: the login service's daemon exits or is killed (D151) | The task's launcher, `mostra-win-service`, starts it again after 10 s, as often as it takes, and logs each exit to `<home>\logs\service.log`; an exit 0 (a clean stop) ends the task. `mostra daemon uninstall` signals the launcher, which sends the daemon Ctrl+Break so it stops cleanly (D87), and ends its job past 15 s |
| On Windows: the login service is removed from another logon session (an SSH session while the user is logged on at the console) (D151) | The launcher's stop event lives in its own session, so `uninstall` stops the daemon with `mostra/shutdown` over the home's pipe, which reaches it from any session; the daemon's exit 0 ends the launcher, then the task is ended and deleted. Nothing is killed while the daemon answers |
| On Windows: the user's session ends (a logoff, a shutdown) while the service runs (D151) | The launcher's hidden window hears it before the session ends and gives the daemon Ctrl+Break, so it stops in order within 4 s; past that the job ends it |
| On Windows: the task is removed in Task Scheduler's own window, or the home loses its definition (D151) | A task Task Scheduler no longer holds stops counting for the idle check within a minute, so a daemon started by hand exits when idle again; `uninstall` removes a task whose definition the home lost |
| On Windows: another user creates the service's stop event first (D151) | Its name has a random part only the user can read, and the launcher refuses an event another user owns: it logs `service.stop_event_taken` and exits 1 rather than take that user's event for its own |
| Worker crashes, OOMs or hangs | Crash or heap exhaustion: the exit is detected. A hang: the 10 s event-loop watchdog kills it. Running action runs end `failed` with reason `interrupted`, and their pages see it. `worker.crashed` is appended. The next request restarts the worker with exponential backoff (1 s to 60 s). Other artifacts and the gateway are unaffected (RT-04; prototype: crash, OOM and hang each isolated) |
| A worker crashes repeatedly (more than 5 crashes in 10 minutes) | The worker is parked. Requests return `MOSTRA_RUNTIME_WORKER_PARKED` (503) with the last cause, `worker.crashed` records `parked: true`, and the shell shows "This artifact's server code keeps crashing" (from the frame ticket's `serverParked` and the event). `verify`, the next publish of the artifact (a republish of the same source too) and a restart of the instance clear the park (D133) |
| A worker answers nothing at all (its process stopped, its channel congested) | Its channel thread answers the watchdog even while artifact code blocks the event loop, so silence is a different failure: after three silent watchdog periods in a row it is stopped as hung ("it answered nothing for N s"), and a single missed ping, such as one queued behind a large result, stops nothing (D133) |
| A watchdog stop while the heap is near its limit (80 % or more) | Reported as out of memory: near the limit, garbage collection stalls the event loop before the heap gives out (seen on Linux) |
| A plain call's or a run's result grows past 16 MiB | The worker's call is cancelled and the call or run ends `MOSTRA_ACTION_TOO_LARGE` (`too-large`); arguments past 16 MiB are refused (413) before a worker sees them (D131) |
| A worker can't be started (its version is damaged, the runtime lacks `@mostra/worker`, its bundle throws while loading) | The call or run fails with `MOSTRA_RUNTIME_WORKER_CRASHED` naming why, and counts as one crash for backoff and parking, its kind (`oom` while loading) included (D136) |
| Builder or verify runner crashes | The operation fails with `MOSTRA_BUILD_CRASHED` or `MOSTRA_VERIFY_CRASHED` plus the child's last stderr lines. Nothing is published. The next operation starts a fresh child |
| A `mostra dev` session's dev server stops, or the source doesn't build (D140 item 12) | The session reports it on `dev/notify` (`diagnostics`, `MOSTRA_BUILD_CRASHED` or the build's codes); a client module that doesn't build shows Vite's error overlay in the page, and server code that doesn't build leaves the last good bundle running. The next change of the source builds again. The connection that started the session closing, `dev/stop` or the instance stopping ends it: its children stop and `cache/dev/<session>/` is removed, and a start removes what a killed instance left |
| PTY host crashes | Live terminals show "Session ended unexpectedly", recordings keep their bytes up to the crash, and a reconnect starts a new PTY host. Other features are unaffected |
| Demo dev server exits | `<WebDemo>` shows the exit code and the last log lines. `mostra open` or a reload restarts it |
| CLI version differs from the daemon's | Protocol negotiation picks the highest common revision. If none exists, the CLI reports `MOSTRA_HOST_REVISION_UNSUPPORTED` with `mostra daemon restart` as the fix. Restarting is safe: everything durable survives, and open views reconnect |

## 3. Persistence

| Failure | Behavior |
|---|---|
| Crash during publish | Staging and build outputs are written outside `versions/`, and promotion is an atomic rename followed by the ledger transaction. A crash before the transaction leaves no visible version (VR-02). The orphaned directory is removed on the next start, because no ledger row names it |
| Crash during a package install | A lock layout counts only once it carries its `.mostra-layout` marker, so the next start removes an unfinished one and the scratch projects of resolutions in progress (`deps/tmp/`). The artifact's working lockfile changes only after its layout is complete, and the store keeps whatever finished downloading |
| Crash between the version rename and the ledger insert | Same as above: the version directory isn't visible without its row, and a later publish of the same digests reuses the directory after checking it |
| Disk full | The transaction fails and the client gets `MOSTRA_HOME_DISK_FULL`. The viewer's unsaved edits stay in the browser journal (§5). Nothing partial is committed |
| Ledger can't be opened (corrupt, unreadable, or not a Mostra ledger) | The supervisor refuses to start with `MOSTRA_HOME_LEDGER_UNREADABLE`. `mostra doctor` runs SQLite's integrity check (through the supervisor, or only when no supervisor holds the lock, D81) and points to the latest backup. Mostra never recreates an empty ledger over an existing file |
| Ledger is newer than the runtime | `MOSTRA_HOME_TOO_NEW` names the schema version and the runtime version that wrote it (DATA_MODEL §6) |
| Migration fails part-way | The migration transaction rolls back, the ledger stays at its old version, and the backup taken before it remains next to the ledger |
| Blob or version file missing or altered | Reads verify content hashes. A mismatch is `MOSTRA_HOME_INTEGRITY` naming the object. The viewer sees "This version is damaged", and the agent gets the code. Publishing the version's source again checks the stored directory against its recorded output digest and rebuilds a missing or altered one in place, under the same version ID and number (WP-03) |
| Home directory removed while running | Writes fail closed. The supervisor checks its home at least every 10 s; when the home is gone it stops accepting requests, answers them with `MOSTRA_HOME_GONE`, stops its children and exits |
| On Windows: a rename or removal meets a file another process holds (an antivirus scan, the indexer) | Retried with backoff for up to 3 s, then the operation fails as on POSIX; a rename is never replaced by a copy, so promotion stays atomic (D150) |
| On Windows: the ledger is removed or replaced while the supervisor runs | Windows refuses: an open ledger can't be removed or renamed, so the home's data stays as it was and the supervisor keeps serving |
| Home owned by another user | Every entry point fails closed with `MOSTRA_HOME_NOT_OWNED` before using it, because the home holds secrets (D44). A home the user owns is tightened to mode 0700 (D85); on Windows, to a protected access list that grants only the user and `SYSTEM`, inherited by everything in it (D150) |
| Control socket path too long for the operating system | `MOSTRA_HOME_SOCKET_TOO_LONG`, naming `MOSTRA_RUNTIME_DIR` as the fix (D82) |

## 4. Submissions and delivery (IN-05, IN-12, IN-13)

**Delivery states:** `pending` → `delivered`. On a terminal rejection: `rejected`, or `undeliverable` for a host-declared terminal reason.

| Case | Behavior |
|---|---|
| Duplicate submit (double click, retry, second tab) | Same request ID or same view and revision: the existing submission is returned. A different view under `once`: typed conflict `MOSTRA_SUBMIT_ALREADY` with the existing submission (H-02). The shell shows "Already submitted" with its time |
| Submit with a stale expected revision | The shell flushes pending saves first. If the server's revision still differs, the submit fails with `MOSTRA_SUBMIT_REVISION_MOVED`, and the shell reloads the draft so the viewer sees exactly what will be sent before confirming again. Invariant: a submission is never made from content the viewer didn't see |
| Submit from an older version's view | Accepted, bound to the version shown, `staleView: true`, with the newer version's number recorded (H-10) |
| Policy `none` | Submit is unavailable, and the shell shows no Submit control. An API call returns `MOSTRA_SUBMIT_POLICY_NONE` |
| Required fields missing | Refused before the transaction, with blockers listed by label |
| Host down when the viewer submits | The submission commits, deliveries stay `pending`, and the viewer sees "Submitted. Pending delivery to <host>". The dispatcher retries with backoff (1 s, doubling to 5 min) while the host is registered, or expected through `HomeConfig.ports`. When the host connects and registers the port, pending deliveries replay in submission order |
| Host accepts, then Mostra crashes before recording it | On restart the delivery is still `pending` and is redelivered with the same `deliveryId`. The host must treat the ID idempotently, and the conformance kit tests that (H-03) |
| A submission's envelope would be longer than one protocol message (64 Mi characters) | Never sent, since the host couldn't read it and every later delivery to that host would wait behind its retries: the delivery is `undeliverable` with reason `too-large: …`, at once. Snapshots are bounded (DATA_MODEL §3), so this is a last defense |
| Host answers `accepted: false, retry: false` | `rejected` (or `undeliverable` when the reason is `undeliverable`; `delivered` when it is `duplicate`, since the host already holds it, D105). The viewer sees the host's reason, and the event is appended. Mostra never retries a terminal answer, and a trigger keeps it final |
| No host takes submissions | The submission goes to Mostra's built-in adapter, which accepts it at once (D58, D105); a host registered or expected (`HomeConfig.ports`) at submit time gets its own delivery |
| Host port call hangs | A 30 s timeout per call counts as a retryable failure |
| Viewer closes the tab right after submitting | Nothing is lost. Delivery is independent of the page. Reopening shows the current delivery state |
| Agent waits during all of this | `wait --until submitted` is satisfied at commit time, whatever the delivery state. "Accepted by Mostra" and "accepted by the host" are separate facts (seed §7) |

## 5. Fields, tabs, devices and offline (IN-01 to IN-04)

| Case | Behavior |
|---|---|
| Two tabs edit different fields | Both mutations apply, because rebase is per field. Each tab receives the other's change on the event stream (BroadcastChannel only shortens the delay) |
| Two tabs or devices edit the same field | The second mutation's base `field_rev` is stale, so it returns a conflict for that field and applies the rest. The writer's field `meta.conflict` offers "keep mine" (a new mutation on the current revision) or "take theirs". Nothing is overwritten silently |
| An agent writes artifact state while a viewer edits the same field | Same rule. The agent's `state/patch` returns `conflicts`, and the viewer's field shows "Changed by <agent>" with the choice (D63) |
| Network drops | Edits go to the IndexedDB journal with their mutation IDs and base revisions, and the field shows `offline`. On reconnect the journal replays in order. Accepted mutations clear, conflicts surface per field, and replays of already-applied IDs return their recorded result |
| The journal holds edits for a version that has since been replaced | Edits replay against their own version's field IDs. Fields missing in the newer version become orphans (D42). Mostra never maps them silently by position |
| Page closed with an unsaved debounce | `pagehide` and `visibilitychange` flush. If the flush can't be sent, the journal holds the edit and replays it the next time any page of that artifact opens in that browser (IN-02) |
| Mutation retried after a timeout | The mutation ID replays the recorded result (IN-01) |
| Field value too large | `MOSTRA_FIELD_TOO_LARGE`. The value is kept locally and not truncated |

## 6. Actions and live data (AC-01 to AC-08)

| Case | Behavior |
|---|---|
| Double click, two tabs or a reload with an explicit key | One run per (artifact, action, key). Later calls join it and stream the same progress and result (AC-03) |
| Double click without a key | Calls join the hook instance's in-flight run. After it finishes, a new click starts a new run, as the author intended |
| Cancellation | The run's `AbortSignal` fires. The run ends `cancelled` if the action stops, or reaches whatever final state the action itself returns (AC-04): an action that ignores the signal and returns ends `succeeded` with its result, so a page never shows "cancelled" for a mail that was sent; a streamed result a cancel cut short ends `cancelled` (D136) |
| A page sends arguments that would outlive the call (symbol names, which `Symbol.for` keeps for the life of the process), a bigint of more than 10,000 digits, an async iterable, or a promise the batches never settle | Refused with 400 `MOSTRA_ACTION_UNSERIALIZABLE` before a run is recorded or a worker sees them; the worker's reader refuses them again. One link holder can't fill a worker's heap and park an artifact for every viewer (D136) |
| A page names a function its version doesn't have | 404 `MOSTRA_ACTION_UNKNOWN_FUNCTION`: no run is recorded, no key spent, no worker started (D130) |
| A version's package layout was removed, or the warm set moved on, before its worker starts | The layout is installed again from the home's store, or a pinned layout with the version's locked warm packages, before the worker starts (D135). Offline with a package the store lacks: `MOSTRA_DEP_OFFLINE` naming it, and the start backs off like a crash |
| Worker crash during a run | `failed` with reason `interrupted` and `MOSTRA_ACTION_INTERRUPTED` naming the cause, no retry (D24). Runs still open when the instance starts (it crashed or was killed) end the same way. An action with external effects should use the provider's own idempotency key. The docs say so, because Mostra's de-duplication covers invocations, not the side effects of a run killed mid-flight |
| An action never returns | Allowed: actions may run long. A busy loop trips the event-loop watchdog. An action awaiting forever just stays `running` until it's cancelled or its worker is evicted (eviction waits for running actions) |
| `verify` meets an action | Invoked only if the action opts in through `dryRun()`. Otherwise the call is skipped and reported (D55) |
| Missing secret | `secret()` throws `MOSTRA_SECRET_MISSING` naming the secret and the `mostra secret set` command. The run fails with that code |
| Host's `secrets` port fails or doesn't answer in 30 s | `secret()` throws `MOSTRA_SECRET_MISSING`; it never falls back to the home's store for a host that took secrets over (D131). A host that isn't connected isn't asked |
| A run's or live update's message is lost (a dropped stream, a full queue) | Updates are ephemeral (D130): the page sees a gap in a run's offsets, a skipped live revision or a reconnect, and reads the run or source again; the ledger holds the truth |
| A keyed run failed | The key stays taken: the run happens at most once (D130), and a page shows its failure. A new attempt takes a new key |
| A `watch` source's file event is missed | The worker also compares the matched files every 2 s (D131, VERIFIED_FACTS WP-08), so the change loads at most that late |
| A daemon has nothing to do | It exits 0 after 30 minutes (D133), unless it runs `--always-on` as the login service or its home has a login service installed |
| Live producer throws or its source is unreachable | The last good value stays, `useLive` exposes `error` with the code, and the producer retries on its schedule. Viewers never see a blank state for a transient error |
| Push to an unknown key | Accepted: pushes create sources (D56). A push whose value exceeds 4 MiB is refused with a code |
| High-rate pushes | Values coalesce: a slow reader's queued values of a source in latest mode give way to its newest, on the server and in the page, which decodes only the newest waiting value and renders at most once per animation frame. Append mode keeps every value, bounded by the ring (AC-08, D136) |
| A home holds thousands of artifacts | Live producers reconcile from an in-memory list of the artifacts whose latest versions have live sources, kept up to date on publish, so a reconcile costs nothing per artifact without them and the supervisor keeps answering (D136) |

## 7. Versions and stale clients

| Case | Behavior |
|---|---|
| New version published while a view is open | The banner appears, with the orphan count. A following viewer switches automatically, unless unsaved edits or orphans would result (D63) |
| Old version's client runtime meets a newer gateway | The gateway serves every browser-protocol revision it ever shipped. Removing a revision needs a 12-month deprecation and a new major version (D32) |
| `mostra gc` | Collects only versions referenced by no submission, view, review set or follow (VR-06). A dry run lists what it would remove. A collected version keeps its ledger row, ID and number; links to it answer `MOSTRA_ARTIFACT_VERSION_COLLECTED`, and publishing its exact source again restores it (D140 item 14) |
| gc meets a publish, a verify run or an install | They never overlap: gc holds the instance's gate alone, the others share it, and a waiting gc goes before work that arrives after it (D140 item 14) |
| A gc step fails (a file it can't remove, the package store's prune) | That step leaves its files and is reported as a `MOSTRA_HOME_GC_INCOMPLETE` warning beside what the run did remove; the other steps run, and the store's index keeps every package the failed prune left. A later `mostra gc` picks up the rest (Opus review of WP-10, finding 1) |
| The process dies during gc | gc marks the versions it collects in one transaction and removes their files after the commit. A crash before the commit leaves everything; one after it leaves files of marked versions, which recovery at the next start removes |
| Artifact source moved or deleted after publish | Versions, submissions and results stay readable from `sources/` and `versions/` (HO-08). The next publish from a new path binds by manifest `id` |

## 8. Network, sessions and addressing

| Case | Behavior |
|---|---|
| Event stream drops | The client reconnects with its cursor and receives every durable event after it. If SSE fails twice in a row, the client switches to long-polling (D47) |
| Daemon restarts while views are open | Same as a drop. Ports are leased, so URLs keep working. Sessions are durable rows, so viewers stay signed in |
| Leased port taken by another program | The gateway leases a new port, records it and logs `MOSTRA_ENV_PORT_TAKEN`. Existing URLs for that artifact stop working, and `mostra open` reissues them. When the shell's port moves, every link minted for the old address answers 410, since the program on that port could read their secrets, and the next publish receipt carries a default link at the new address (D97 item 10). `mostra doctor` names the conflicting process where it can |
| Token expired or revoked | 410 with `MOSTRA_HYGIENE_TOKEN_REVOKED`. The shell explains "This link was revoked or has expired" and keeps any unsaved local edits in the journal (HY-03) |
| Bad Host, bad Origin, missing token or missing CSRF header | 403, 421 or 401 with a code, logged without the request's capability material (HY-01) |
| Guessing a token | Past 30 failed tokens for one artifact in a minute, every token for it gets 429 with `Retry-After`, a right one too; other artifacts' links keep working (D97 item 8) |
| Another link opened for an artifact this browser already has open | The shell shows what each link allows and asks which to keep; nothing is replaced until the viewer chooses (D98 item 8) |
| A page fills the host's cookie jar | Up to 1 MiB of headers, more than browsers keep per host, is served. Past that, 431 `MOSTRA_HYGIENE_HEADERS_TOO_LARGE` with a page that clears the host's cookies; the viewer opens the link again (D98 item 9) |
| A version's files altered or removed while the gateway runs | The next request for one of its files checks the version again and answers 500 `MOSTRA_HOME_INTEGRITY` until a republish rebuilds it (§3, D98 item 5) |
| Tunnel drops | Viewers over the tunnel reconnect when it returns. A Tailscale tunnel whose process ended is started again (after 1, 4 and 16 s) on the same address; one that can't be, and a Cloudflare quick tunnel, whose address dies with its process, end every share that used them (`share.stopped`, reason `tunnel`), which `mostra share list --all` reports. Public shares never fall back to a wider bind, and faces bind loopback whatever `--bind` says (D158) |
| A tailnet viewer can't reach a share: the tailnet's access policy doesn't allow its ports, the viewer's browser resolves the device name through public DNS while Funnel runs on it, or split tunneling leaves the browser out | The page hangs on the viewer's side and no request reaches the gateway, so Mostra can't tell the viewer. `mostra share --tailnet` names the two ports of the device the policy must allow and says the browser's traffic must go through Tailscale; `Share.artifactOrigin` gives hosts the second port (D158 item 8) |
| The instance restarts while shares are active (D158) | Tailnet and Funnel shares are set up again from their recorded plans on the same addresses (retried for about two minutes while Tailscale starts), so their links keep working; a Cloudflare share ends (reason `restart`), since its address can't be had again; a share whose link expired or was revoked meanwhile ends with that reason |
| A share's link expires, is revoked with `view/revoke`, or is rotated with `view/rotate` (D158) | The share ends at its TTL or within 30 s of the revocation: its tunnels stop when no other share uses them, and its faces close. A rotated link stays at the share's address and the share follows it (`Share.tokenId` and `url` name the replacement); only revoking ends it |
| A tunnel or proxy holds an event stream back (a Cloudflare quick tunnel, a buffering proxy before a host's external base) (D158) | The gateway refuses streams on faces it knows streams don't pass, and every stream opens with `ready`: a page or shell that hears nothing within 6 s of opening long-polls instead, on the same cursor |
| A request through a Funnel or Cloudflare share, or past the tunnel, carries `Tailscale-User-*` headers (D158 item 2) | They name nobody: identity headers count only on a tailnet face, from a loopback peer, and never beside `Tailscale-Funnel-Request`; the session acts as its link's own viewer |
| The host's `addressing` port fails, is away, or answers `null` (HO-10) | A failure or an absence keeps the face it gave before (its links keep working), else links stay on loopback; `null` or another origin withdraws the face, and its links stop working at once |
| The artifact's frame fails to load (a connection the browser couldn't make, such as Chromium's `ERR_NO_BUFFER_SPACE` on Windows, or a request never answered) | The shell enters the frame again with a new ticket when it loaded without greeting within 6 s, or greeted nothing within 12 s, up to three times with a pause of 1, 2 and 4 s (`verify` once), then says the page didn't load; a page that greets later is shown, a ticket asked for before the frame greeted is dropped, and each ticket request has 10 s. Nothing typed is lost: a frame that never greeted ran no client runtime. Gateway listeners keep idle connections 305 s so browsers close them, which leaves the gateway no closed connections for random ports to collide with (D157). In `verify`, a render where any request of the page, or the shell page's own load, failed with exactly `net::ERR_NO_BUFFER_SPACE` is rendered once more in a fresh context while 5 s are left, and that render answers (D168 item 12, #132) |
| Worker-mode frame bootstrap fails (service worker blocked) | The shell shows `MOSTRA_HYGIENE_FRAME_SESSION`, with the reason and a suggestion to open the tailnet or Funnel link instead (D70), and stops loading the frame again, which wouldn't help. A bootstrap that is only slow has 25 s to say it entered before the shell enters the frame again |
| Artifact code registers a service worker in a worker-mode frame (D70) | The client runtime refuses it with `MOSTRA_HYGIENE_FRAME_SESSION` (a rejected promise and a console error), since its script would be fetched without the session and a page it controlled would lose its own; Mostra's worker keeps signing the page. On a tailnet, Funnel or local link the artifact registers its own workers |

## 9. Timeouts

| Operation | Default | On timeout |
|---|---|---|
| `wait` | caller-chosen (CLI) or 50 s at most per MCP call | `still_waiting` with a cursor and nothing lost (IN-10) |
| `verify` | 120 s for every stage after compile, the baseline's render included; the smoke test 60 s or 200 interactions; installs keep their 300 s and the build its 180 s, with the type check beside the build inside the same 180 s (D138) | Partial verdict with `MOSTRA_VERIFY_TIMEOUT` (an error) and the stage reached; a smoke test at its budget stops with a hint and nothing else |
| Build | 180 s | `MOSTRA_BUILD_TIMEOUT` |
| Package install | 300 s, or immediate when offline | `MOSTRA_DEP_TIMEOUT`, or `MOSTRA_DEP_OFFLINE` naming the package (DP-04) |
| Port calls to hosts | 30 s | Retryable failure (§4) |
| Protocol requests from clients | none by default; the client sets `timeoutMs` | The client abandons the request; durable effects keep their IDs |

## 10. Configuration and platform

| Case | Behavior |
|---|---|
| The CLI's telemetry settings file can't be read or parsed | Telemetry is off: nothing is sent, nothing crashes, no exit code changes, and `mostra telemetry status` names the file (D140 item 5). Only `mostra telemetry on` or `off` writes over it |
| The telemetry collector can't be reached, or answers slowly | No command waits for it: a detached flusher posts the queue after the command, and keeps what it couldn't send for the next flush; past 1,000 events or 7 days the oldest are dropped (D140 item 6) |
| Manifest isn't a literal, or is invalid | `verify` and `publish` report `MOSTRA_MANIFEST_*` with the location and a fix. Unknown keys are warnings, so manifests evolve additively |
| Unknown import with `dependencies: "explicit"` | `MOSTRA_DEP_MISSING` with the exact `mostra add` command (D43) |
| Package lifecycle script fails | The install fails with `MOSTRA_DEP_INSTALL_FAILED` and the script's output; nothing is published. It runs in an install child with the artifact's directory and environment, never in the supervisor (DP-05) |
| Registry unreachable, or a package the store lacks while offline | `MOSTRA_DEP_OFFLINE` naming the package; with `MOSTRA_OFFLINE` set or no network interface up, the supervisor answers from its store index before any child starts (DP-04). Everything the store holds keeps building, including rebuilds of published versions |
| No such package or version, or only releases younger than a day for a spec without an exact version | `MOSTRA_DEP_NOT_FOUND` with the registry's answer (D95) |
| Unsupported platform (any but macOS, glibc Linux and Windows on x64 and arm64, D146) | Every entry point fails closed with `MOSTRA_PLATFORM_UNSUPPORTED` before touching the home (D35), and the SDK and the crate before any download. `mostra-runtime host` also answers the host's first request with it, so a spawning host gets a typed error |
| An editor holds a file `mostra dev` mirrors (Windows), or saves by moving the old file aside (D151) | The file is mirrored on the next sync (file events and a 1 s comparison), never lost; a file is removed from the preview only once it has been missing for 1.5 s, which a save never takes, on every system |
| On Windows, a program binds a port on every interface (D151) | The firewall blocks it and asks the user (event 5031). The gateway binds loopback only unless `--bind` widens it (D99), so it is never blocked and nobody is asked; the gateway suite proves both with the firewall's audit |
| On Windows, the runtime can't find its helper `mostra-win.exe` | `MOSTRA_ENV_HELPER_MISSING` before the home is touched, naming where it looked (D150) |
| No browser available for `verify` | `MOSTRA_ENV_BROWSER_MISSING` with the install command. Inside a runtime bundle the browser is fetched and checked at setup (D142 item 2), so this means its setup didn't finish: `bin/mostra-setup` finishes it |
| A runtime bundle's archive differs from its pin (size or SHA-256), holds an entry outside its directory or of another kind than files, directories and links, or a file, link or execute bit differs from `files.json` (D142) | `MOSTRA_ENV_BUNDLE_INVALID` naming what differs; nothing is installed or run, and the scratch directory is removed. A download that grows past the pinned size stops at once. `mostra doctor --deep` reports a cached bundle changed after setup the same way |
| The download fails: the network, a proxy, a mirror's 5xx, a stalled transfer, a full disk | `MOSTRA_ENV_BUNDLE_DOWNLOAD_FAILED`. Server errors, 408, 429 and stalls (60 s without bytes) are tried three times in all (again after 1 s, then 4 s); a 4xx otherwise, a size or digest that differs, a full disk and an abort are not retried. Free space is checked before the download (the archive, its unpacked size and 500 MiB for the browser). Nothing half-made is left where a bundle is expected |
| Offline (`MOSTRA_OFFLINE`), or no bundle for this release and platform | Only the cache serves; without a cached bundle, `MOSTRA_ENV_BUNDLE_UNAVAILABLE` names the release and platform before any network use |
| A Windows bundle's archive holds a link, its `files.json` lists a link to a file, or setup would make a junction over a real file or directory or point one outside the bundle (D153) | `MOSTRA_ENV_BUNDLE_INVALID`; an archive with a link is refused before anything is extracted, and setup writes no marker, so nothing runs from the bundle |
| A Windows bundle moved or copied after its setup (its junctions name the old directory, D153) | Its setup marker names another root, so the bundle counts as not set up: the next use sets it up again, which makes its junctions afresh and checks every file, without downloading anything. A copy made by a tool that follows junctions holds real directories where the links belong: each that holds exactly its link's target is replaced by the junction, and one holding anything else is refused (`MOSTRA_ENV_BUNDLE_INVALID`) and kept. Two setups of one bundle at once each accept the junctions the other made |
| A rename into the cache meets a sharing violation on Windows (an antivirus scan, the indexer) | Tried again with backoff for up to 3 s, as the runtime's renames are (D150 item 8); a refusal that lasts is `MOSTRA_ENV_BUNDLE_DOWNLOAD_FAILED`, and the scratch directory is removed |
| The browser's fetch fails or differs from its pin at setup | The bundle stays installed but unready (no setup marker): `MOSTRA_ENV_BUNDLE_DOWNLOAD_FAILED` or `MOSTRA_ENV_BUNDLE_INVALID`, and the next use finishes setup without downloading the archive again |
| Two installers of one bundle at once (two hosts, a CLI and an SDK) | One holds the bundle's lock and downloads; the other waits and uses its result. A lock whose owner died, or older than an hour, is taken over (moved aside and removed only if it is the file judged stale). Should both ever extract, each works in its own scratch directory and the one that loses the rename uses the winner's checked bundle |
| A crash during an install | Scratch directories (`.tmp-<pid>-…`) whose process is gone are removed by the next install; the lock is taken over as above |
| A release fails part-way (D142 item 9) | Before its GitHub release is published nothing is on npm, and the next run replaces the draft's assets with its own. After it is published, the next run (a re-run, or the next push to `main`) finishes it: it builds from the release's tag, pins the release's own archives and publishes only what npm lacks, skipping a package only when npm holds exactly that tarball; other bytes on npm fail the run before anything is published. npm holding a version whose release isn't published fails the run closed. Nothing published is ever deleted or moved |
| `mostra` or `npm create mostra` from npm started on a Node.js older than 22.19 | `MOSTRA_ENV_NODE_UNSUPPORTED` (exit 3, one `--json` envelope) before anything else loads and before any download; npm itself only warns about `engines`, so the gate is the CLI's first statement. The SDK needs 22.19 too (its `engines`). Inside the bundle every Mostra process runs on the bundle's own Node.js |
| Required tool missing for sharing | `MOSTRA_SHARE_TOOL_MISSING` with install instructions (D47) |

### 11.1 The owner offline, and the relay (D165 item 4)

| Case | Behavior |
|---|---|
| The owner's machine sleeps while hosted links are used | Pages, drafts, submissions, comments, artifact state and links keep working on the hosted home. A respondent sees "Your answer was sent." once the hosted home commits (D165 item 1a); the owner later sees each delivery's state. Deliveries to the owner instance wait, in order (D105). Live sources show their last value with its time and `ownerOffline` |
| An action is pressed while the owner is offline | The run is recorded `waiting` and the page says it waits for the owner. Under `hosted.offline.actions: "queue"` it starts when the owner returns, unless its limit (24 h by default, 7 d at most, counted from when it was recorded) passes first, which ends it `failed` with reason `owner-offline`: it was never sent, so it never happened. Under `"fail"` it ends so at once. Cancelling it before it is sent ends it `cancelled` without contacting the owner. A plain call answers `MOSTRA_REMOTE_OWNER_OFFLINE` at once |
| The owner accepted a run, but its acknowledgement was lost | The hosted home has no `accepted_at`, so it sends the run again on reconnect, which joins the owner's record; the run happens once. A run sent but never acknowledged is never `failed` for the owner's absence: at its limit it becomes `unknown` |
| After a reconnect, the owner has runs it accepted and hasn't finished | The hosted home reconciles them (`port/relay.reconcile`): each gets its state from the owner; one the owner doesn't know becomes `unknown` at once and is never sent again |
| The owner's home was restored from a backup taken before runs it accepted | Its `relayMark` is below the highest sequence the hosted home saw it accept, so every run it accepted and hasn't finished, and every run sent but not acknowledged, becomes `unknown` and is never sent again. The one window left: a run the owner recorded and started whose acknowledgement was lost in the moments before its home was then restored to an earlier backup can run a second time when sent again. That is the relay's one accepted boundary |
| Waiting runs reach the cap (`relay.waitingRunsPerArtifact`, or a `limits` refusal of `run.wait`) | A new run is refused with 503 `MOSTRA_REMOTE_QUEUE_FULL` before anything is recorded; the page says so and nothing is half-made. Runs already waiting keep their place |
| The owner returns after a day of queued runs | Waiting runs go out in the order they were recorded, at most `relay.drainPerSecond` a second per artifact, so the owner's machine isn't flooded; each runs once (its run ID) |
| The relay is lost while a run runs (the owner's network drops, the server or an edge restarts) | The owner instance finishes the run and keeps its updates; on reconnect it sends what the hosted home hasn't acknowledged, by `(runId, seq)`, then the end. Meanwhile the hosted run shows `running` with `ownerUnreachable`. A cancel pressed meanwhile is delivered on reconnect and reaches the run's `abortSignal` if it still runs |
| The owner never reports the run's end within the offline limit | The run becomes `unknown` (outcome unknown, `action.unknown`): never `failed`, because the action may have taken effect. Waits and the page stop treating it as running. If the owner reports later, the reported end replaces `unknown` once and appends its own event |
| The owner instance crashes or is killed during a relayed run | Its run ends `failed` with reason `interrupted` in its own ledger (§6), never retried (D24), and the end is sent on reconnect |
| An update from the owner starts past what the hosted home holds (one before it was lost on a live binding) (WP-29, D166 item 22) | Nothing of it is kept, its end least of all; the hosted home asks the owner for the run from what it holds, and the owner's answer brings the rest. The owner answers a repeated `port/relay.run` with the run's whole state, and a run's end carries its whole output, so a run never ends without its result |
| The owner redials while the server still holds its old connection (a network change) (D166 item 22) | The newest session of a link is its own; once the old one closes, the new one is reconciled and drains. A reconcile that fails is tried again for its session, 1 s doubling to 60 s |
| A relay message arrives twice (a retry after a reconnect, an edge replaying a request) | `port/relay.run` with a known run ID answers as before and starts nothing; updates are idempotent by `(runId, seq)`; a `key` keeps D130's at-most-once rule. Exactly once in effect holds across both homes |
| A relayed run's server code reads a secret | The owner's supervisor answers it (D129); no relay message carries it, and every update passes the owner's redactor (AC-06) |
| A viewer who isn't signed in presses a relayed action under the default `hosted.actions: "signed-in"` | 403 `MOSTRA_REMOTE_SIGN_IN_REQUIRED`; the shell offers sign-in, and nothing is recorded (D159) |
| Flooding a link's relayed actions | Past `rateLimits.perLink.relayedRuns`, 429 `MOSTRA_REMOTE_RATE_LIMITED` with `Retry-After`, before anything is recorded or relayed |
| Authoring from a chat host with no connected default instance | `artifact_create`, `artifact_verify` and `artifact_publish` answer `MOSTRA_REMOTE_NO_INSTANCE`, saying to start Mostra on the linked machine; reading tools keep working (D165 item 5) |
| A message for an artifact whose owner instance is another one | The hosted home never sends it to this instance: only the artifact's owner link receives its deliveries (one per submission), relayed runs and authoring calls, and the follow imports nothing of it. A `hosted/push` or `share/start` from another instance of the account for an artifact it doesn't own is refused with `MOSTRA_REMOTE_NOT_OWNER_INSTANCE`, naming the owning instance (D165 item 1b) |

### 11.2 The link, sync and the server

| Case | Behavior |
|---|---|
| The binding's connection goes silent | Each side pings every 20 s; after 45 s with nothing received it closes and dials again with backoff (1 s doubling to 60 s, with jitter). Ordinary reconnect: the session is opened afresh, ports registered again, pending deliveries and relay messages resume (D165 item 2) |
| The server, its edge or a proxy restarts | The same reconnect. Hosted homes are reopened on their next request; every acknowledged write was committed (§1 rule 1). Viewers' streams reconnect with their cursors (§8) |
| A message longer than the line limit, or a binary frame | The receiver closes the connection (1009 or 1003) and logs `MOSTRA_HOST_MESSAGE_TOO_LARGE`; the sender never sends one, since submissions are bounded (DATA_MODEL §3) and bulk bytes go over HTTPS |
| The server refuses a push for good (another instance owns the artifact, a damaged version) (D166 item 22) | The push is `refused`, named in `remote/status`'s `lastError`, and never tried again; later publishes to that server still go out. A first share refused leaves the artifact unshared there |
| A followed submission the owner doesn't hold can't be read again at once (the binding drops, the call times out) (D166 item 22) | It waits in `remote_missing`, written with the cursor that passed it, and is read again at every page and session until imported. A page of followed events that can't be copied ends the connection, so no later page commits the cursor past it |
| A version push is interrupted | Files are content-addressed and the push is idempotent by version ID: the next attempt sends only what `hosted/push` still names as missing. Publishes made while the server is unreachable wait in `version_push` and go in order when it returns; hosted viewers keep the version they have |
| A pushed file's bytes don't match its name, or the listing doesn't match `outputDigest` | Refused (`MOSTRA_HOME_INTEGRITY`); nothing of the version is visible until a push completes |
| A delivery to the owner instance is repeated (the owner committed it but the acknowledgement was lost) | The owner finds the submission by its ID and answers `accepted`; its own hosts got one delivery (D105) |
| The sync cursor falls behind a compaction on the hosted home | The follow receives `artifact.compacted` with `MOSTRA_HOST_CURSOR_COMPACTED` (DATA_MODEL §4) and continues after it; submissions are never lost, since they arrive by delivery, not by the follow. Local waits on events inside the range answer the same code |
| The owner's home is restored from a backup, or a second machine links | A restored home resumes from its stored `follow_cursor` and the server's acknowledged cursor, whichever is lower, so events repeat rather than go missing, and their `origin` makes each appear once. A submission it had accepted after the backup is missing locally, so the followed `submission.created` imports it again from the hosted home, which keeps every one, and its local delivery repeats its derived `deliveryId`, so a host that dedupes by it sees one delivery. Its relayed runs are reconciled as in §11.1. A second instance of the account reads and waits through the hosted home and receives nothing (D165 item 1b) |
| A hosted home is restored from its backup (its machine was lost) | The copy lags the lost home by the replicator's delay (about a second). Whatever was committed in that window is gone from the server: drafts, events and submissions whose respondents were told "Your answer was sent." The home's incarnation rotates, so its reused cursors are never taken for ones the owner copied. The usual restore brings back the whole data directory, whose recorded high-water marks are as old as the home, so the owner instance is the witness: when its committed cursor or its relay mark is above what the home holds, the home rotates before answering it. `ServerHandle.restored`, `mostra-runtime server --restored` and a home opening below its recorded mark rotate it too. The owner continues after the restored head under the new incarnation, keeps every submission and event it already imported (a submission delivered to it before the loss is safe there), and appends `remote.regressed` naming the window. The home's relay sequences continue above the owner's relay mark, so none is reused; an owner's update for a run the restored home no longer knows is dropped and logged, and the owner keeps and finishes that run locally. A viewer's page that resumes above the head gets a fresh snapshot, never an empty tail. WP-29 restores a lagging copy of the whole directory under traffic and checks both sides |
| An operator moves a home to another data directory | `drainHome` closes it and refuses to reopen it until `releaseHome` on the new machine, so two copies never serve at once; requests meanwhile answer 503 and clients retry |
| The owner instance is gone for good (the machine is lost) | Its hosted artifacts keep serving pages, drafts and submissions; their runs wait or fail by their policy, and deliveries stay pending. Moving an artifact to another owner instance is additive later (D165 item 1b) |
| The account's sign-in is revoked, or the refresh token expires | The binding is refused (401), and an open binding is closed within 60 s of a revocation or suspension. `remote/status` says `signed-out` and `mostra login` links again, rebinding the same instance link, so its artifacts stay its own; a revoked grant never removes an owner link. Hosted pages keep working; deliveries and runs wait for the owner as when it is offline |
| An open binding's access token expires | The client sends a fresh one in band (`remote/token`) before it does; otherwise the server closes the connection at the expiry and the client reconnects with a refreshed token |
| Two parallel refreshes of one refresh token (a client refreshing from two surfaces) | Within 30 s of the rotation the old token returns the same successor; a use after that counts as reuse and revokes the grant |
| A write to a hosted artifact's state or live value while the server can't be reached | Refused with `MOSTRA_REMOTE_UNREACHABLE`, never applied locally alone (D165 item 1); a local view's field shows `offline` and its journal keeps the edit (§5) |
| Two server processes on one data directory, or a hosted home | The second can't take `server.lock` or the home's `home.lock` and refuses (`MOSTRA_HOME_LOCKED`); the operating system releases a lock when its process dies, so a crashed server never blocks the next |
| A data directory on a network filesystem | The server refuses to start (`MOSTRA_HOME_NETWORK_FILESYSTEM`), since its locks and WAL need a local disk (D165 item 0b) |
| A home is opened while closing for idleness | The registry serializes it: the request waits for the close to finish, then opens the home; a home never has two writers in one process |
| A hosted domain is flagged, and the operator moves the active domain | New links use the new active domain; links already issued keep resolving on theirs (D137). No release is needed |

### 11.3 Viewers, sessions and limits

| Case | Behavior |
|---|---|
| A tenant page tosses a cookie onto the parent domain, names one like a session, or fills the jar past 180 cookies | Nothing changes: hosted sessions use no cookies, and the server drops every `Cookie` header unread (D165 item 8). WP-30 seeds all three |
| Tenant pages fill the site's storage group (Firefox's 10 GiB group, or the disk) | New writes on the apex fail: the shell keeps the session in memory, leaves the link's fragment in place until the secret is stored, and tells the viewer that reloading will need the link again. No session is taken over; WP-30 seeds a sibling filling the group |
| Two accounts host one artifact ID (a copied project), or one pushes an ID it saw in another's link | Each gets its own hosted route with its own random ID and label: both host, and neither can take or block the other's (routes are keyed by home and artifact) |
| A removed artifact's ID is pushed again by another account, or an operator gives away a label | A new route gets a new label; an issued label is never issued again nor moved to another home, so the old origin, with its storage in every viewer's browser, is never served again |
| One browser visits two owners' hosted pages without signing in | Each route receives a different anonymous key, derived from one browser secret, so the two owners can't recognize the same visitor |
| A script injection is attempted through tenant text the shell shows (an owner's name, a title, a pause or quarantine reason) | The shell renders such strings only as text, under a CSP with no inline script and Trusted Types; a session secret sent with another route's path is refused anyway |
| A page starts sign-in on its own, or a sign-in code is redeemed for another page (login CSRF) | Sign-in starts only from a click in the trusted chrome; `state` is bound to the route and the shell session and checked on return, so the code is refused elsewhere; the authorization server names the page's sender before the person is named to them |
| A client registered with an attacker's redirect URI sends a victim an authorize link, and the identity provider approves silently | The authorization server's own consent page names the client (unverified) and its redirect host, and no code is issued without consent for that client; an approval of one client never carries to another |
| A device code an attacker started is approved by a victim | The device page says approving links a machine to the account, and to continue only if the person started it; the new instance link appears in `remote/status` and as `instance.linked` |
| A client's metadata document URL points at a private or loopback address, or redirects there | Refused before any fetch: the name is resolved and private, loopback, link-local and metadata addresses are refused on every connection, redirects aren't followed, and size and time are bounded |
| A visitor rotates IPv6 addresses, or sends a forged `X-Forwarded-For` | Rate limits key IPv6 per /64 by default, and `X-Forwarded-For` is read from the right, skipping trusted proxies, so a forged leftmost address is ignored |
| One home asks whether the server holds a file with a given hash, or names another home's bytes in a push | Answers only reflect the asking home's own files, and uploads are accepted only for its pending push's missing files, so it learns nothing of other homes and must send every byte of its own versions |
| Safari deletes the shell's storage after 7 days without a visit (VERIFIED_FACTS, WP-28) | An anonymous viewer who returns starts afresh: their earlier draft and their `once` marker are no longer theirs (best effort, D165 item 13). A signed-in viewer signs in again and finds their drafts, which belong to the account. A frame's worker registration is made again at its next entry |
| The user-content domain later becomes a public suffix | Nothing in a session changes, since none depends on the shell and its frames being one site (D137). Safari then treats each frame as third-party, whose storage is partitioned and ephemeral (VERIFIED_FACTS, WP-28): a frame's worker registration is made again at each entry, as already, and its journal of unsent edits lasts only the browser's session, so an edit made offline and never sent before Safari quits is lost there |
| A burst of anonymous submissions while the owner is offline | Accepted durably at the targets (D165 item 13). Past a per-IP or per-link rate limit, 429 `MOSTRA_REMOTE_RATE_LIMITED` with `Retry-After`: the shell says "try again shortly" and keeps the draft; nothing is dropped silently. The queue of deliveries to the owner drains in order when it returns, and its agent reads every new submission since its cursor in one result |
| `once` for an anonymous viewer, from a second browser or after storage was cleared | A second submission is accepted as another viewer's: `once` per anonymous viewer is per browser, best effort, and the submission is recorded unverified |
| An operator's `limits` refuses an operation | A share, push, link or authoring call answers the operator's code (`MOSTRA_REMOTE_LIMIT_REACHED` with its message); a refused submission keeps the draft and the shell says the page isn't accepting answers right now. A view the operator refuses shows the operator's message from the shell |
| The operator module doesn't answer in time (2 s for `limits`, `policy` and `routing`, 5 s for `accounts`) | Operations that create fail closed with 503 `MOSTRA_REMOTE_OPERATOR_UNAVAILABLE`; views, drafts and submissions proceed, so nothing a person typed is lost (D165 item 9). Sign-in fails with the same code and existing sessions keep working. An unknown host with no routing answer gets 421 |
| Metering or outbound events can't be delivered | Kept in `outbound` and retried with backoff across restarts, idempotent by `batchId` and `eventId`; nothing waits for them. A gap the server had to drop is logged |
| An artifact is paused | Views keep working and the shell shows it paused; submissions answer 423 `MOSTRA_SUBMIT_PAUSED` and relayed actions 423 `MOSTRA_ACTION_PAUSED`, each keeping the draft; links stay valid. The owner resumes an owner's pause; only the operator resumes its own (`MOSTRA_REMOTE_PAUSED_BY_OPERATOR`) |
| The operator quarantines a version or artifact | Its links show a neutral "under review" page from the shell; data is kept, and `release` restores it. Every handle target names a hosted route, so quarantining, pausing or removing one route never touches another home that hosts the same artifact ID or an identical version |
| An MCP client's token is invalid, expired or for another resource | 401 with `WWW-Authenticate: Bearer resource_metadata="…"`; the client refreshes or signs in again. A reused refresh token revokes its grant (D165 item 10) |
| A front before the server passes fewer headers than a filled cookie jar sends (D167 item 15) | The server takes up to 1 MiB and drops every cookie unread, so the front decides: one that refuses large headers (Caddy's default is 16 KiB) fails every page on the domain for that browser. The self-hosting page raises Caddy's limit to 1 MiB |
| An operator's answer is malformed (D167 item 2) | Counted as no answer, logged: the port's no-answer rule applies, as for a timeout |
| An operator answers a host it gave one home for another (D167 item 6) | Refused and logged; the host keeps serving the home it was first given, and an unknown host still gets 421 |
| The server stops, or an instance stops its gateway (D167 item 18) | Every open connection is reset, not closed, so none stays in TIME_WAIT on the listener's port; a browser reconnects to the next instance on the same leased port without `ERR_NO_BUFFER_SPACE` on Windows (#132) |

### 11.4 Teams (D168)

| Case | Behavior |
|---|---|
| The roster changes while `submitted:all` is pending | Each change settles the roster in its own transaction: a respondent added makes a complete round incomplete again, so the wait goes on until they answer too; the last respondent who hadn't answered removed completes the round, with its `roster.completed`, and the wait returns |
| The last respondent's submission commits | `roster.completed` is appended in that transaction, so a wait never sees the submission without the completion or the completion without it; a crash before the commit leaves neither |
| An owner instance follows a hosted completion before the submissions it names are delivered | `submitted:all` waits until every one is imported, so `results` then holds them all; deliveries come in order (D105) |
| A respondent's personal link was revoked or expired | `roster/add` for them again mints a new link (`relinked`); their draft and submissions stay theirs, as they belong to their viewer |
| A respondent is added again with other scopes, another version or an expiry | They get a new link that matches (`relinked`, a new invitation where one is sent); the old one isn't revoked, since they may hold it, and keeps acting as the same viewer |
| `roster/add` past 1,000 respondents | Refused whole with `MOSTRA_TEAM_ROSTER_TOO_LARGE`, nothing added |
| `submitted:all` or `submitted:<N>` (N > 1) under `once` per artifact | Refused at once with `MOSTRA_TEAM_ROSTER_POLICY`: one submission in all can never satisfy it |
| A page posts presence faster than 20 updates a second | 429 `MOSTRA_TEAM_PRESENCE_RATE_LIMITED` with `Retry-After`; nothing else changes, and the client waits it out and sends its latest state. The view's bucket outlives its presence, so leaving and joining again never refills it; a present view's leave is honored at once, so a page that goes after a burst of cursor moves is gone for the others |
| A page closes, crashes or loses its network without leaving | Its presence lapses after 30 s without a renewal, and the others see it gone |
| A presence update is still on its way when the page leaves (an unmount, `pagehide`), and reaches the gateway after the leave | Its `seq` is older than the leave's, so it changes nothing and the page stays gone; its answer, when it comes, is ignored by the page. The post still takes its token, so old counts never escape the rate |
| A page comes back from the browser's back/forward cache | It left as it went (`pagehide`), and joins again on `pageshow` with its hooks still mounted |
| The instance restarts | Presence starts empty (it is never stored); pages join again with their next renewal. Rosters, rounds and roster events are durable |
| A version built before WP-31 is open | It never asks for team traffic, so it never receives a message kind it doesn't know |
