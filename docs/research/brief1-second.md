# Agent Artifact Runtime Landscape and Positioning

## Executive conclusion

**Verified market direction.** As of October 9, 2026, the market has converged on several distinct layers that are often all called “generative UI,” but they solve different problems. OpenAI’s new Intelligent UI, launched October 7, generates progressively streamed interfaces from a native component library and compiler inside ChatGPT; Claude Artifacts provides persistent, shareable interactive artifacts inside Claude; coding platforms such as v0, Bolt, Lovable, and Replit generate ordinary applications; AG-UI standardizes agent↔frontend events; A2UI standardizes declarative agent-generated UI; and MCP Apps standardizes sandboxed HTML applications delivered by MCP tools. OpenAI now explicitly recommends the MCP Apps bridge as the standards-first foundation for new ChatGPT app UIs. citeturn21view0turn1search2turn19search23turn19search18turn21view3turn20search1

The most important new entrant is **CopilotKit’s Open Intelligent UI, released today, October 9, 2026**. It allows an agent to generate working charts, maps, Three.js scenes, calculators, games, and other interfaces, streams them while generating, executes generated code in an isolated iframe with an approved-CDN policy, can download the result as standalone HTML, and connects agents through AG-UI. That moves open-source generative UI materially closer to the proposed toolkit than the 2025-era landscape did. citeturn22view0

**Judgment.** Even after that launch, there is still a defensible category for the proposed project. It should **not position itself as another generative-UI framework, chat frontend, AI website builder, declarative UI protocol, or MCP UI SDK.** The strongest position is:

> **An open-source, local-first runtime and host bridge for agent-authored interactive software artifacts.**

The unit of authorship is ordinary source code—React/TypeScript, optionally MDX—not a model-specific UI message, schema, fixed component catalog, or hosted-project abstraction. The runtime supplies what normal React does not: durable human input, submissions back to an agent/host, server actions, identity, live resources, review/comment semantics, terminal/TUI capture, screenshots and diagnostics for blind coding agents, presentation modes, packaging, and host integration.

That distinction matters because the closest systems optimize different boundaries. Claude Artifacts and ChatGPT Intelligent UI optimize **a particular AI host**; v0/Lovable/Replit/Bolt optimize **building and deploying applications**; AI SDK/CopilotKit/assistant-ui optimize **AI applications and conversations**; MCP Apps optimizes **portable tool-supplied iframe UI**; A2UI optimizes **safe declarative cross-platform rendering**; Streamlit/Gradio/Marimo optimize **fast Python data applications**; and Slidev/Quarto/Spectacle optimize **documents and presentations**. citeturn21view0turn0search2turn6search16turn6search22turn7search0turn5search0turn4search2turn21view3turn19search18turn16search5turn18search0

The recommended architecture is therefore **standalone-first, adapters-outward**: keep an unrestricted React runtime as the internal model; make host capabilities typed ports; ship a standalone SQLite/default-server implementation; export artifacts into MCP Apps; optionally expose the runtime itself as an MCP server; map long-running agent interaction onto AG-UI when needed; treat OpenAI Apps SDK functionality as a small MCP-Apps-plus-ChatGPT extension; and support A2UI as an optional guest format rather than as the project’s intermediate representation.

Two trends are particularly important.

First, **the ecosystem is separating transport from UI representation**. Second, **arbitrary-code UI has not disappeared despite the rise of safe declarative formats**. MCP Apps explicitly embeds HTML/JS apps in sandboxed iframes, Open Intelligent UI executes generated code in isolated frames, and Google now documents hybrid architectures where an A2UI surface embeds an MCP App for complex stateful behavior. ## Gap analysis and recommended positioning

### Where existing systems overlap

A number of capabilities in the brief are no longer individually novel.

Persistent state is available in current Claude Artifacts, ordinary full-stack apps generated by Lovable/Replit can obviously persist data, and assistant-ui has persistence abstractions. citeturn1search2turn6search21turn6search1turn4search13 Real actions are possible through MCP Apps tool calls, OpenAI’s ChatGPT app bridge, Claude connectors and ordinary application backends. citeturn21view3turn3search0turn1search6 Arbitrary application UI can be embedded through MCP Apps or generated inside Open Intelligent UI’s iframe. citeturn21view3turn22view0 Replit even treats multiple artifact types as siblings sharing backend resources. citeturn6search22

The opportunity is therefore **the composition of these ideas around coding-agent authorship**, not claiming that every constituent feature is unprecedented.

### Position the project one layer below “generative UI”

The conceptual stack should look like this:

```text
Agent / coding harness
        │
        │ CLI, process API, optional MCP / AG-UI adapters
        ▼
┌─────────────────────────────────────────────────┐
│ Agent Artifact Runtime                          │
│                                                 │
│ source: React / TypeScript / optional MDX       │
│ runtime: dev server, HMR, backend actions       │
│ services: storage, submission, identity, events │
│           live data, reviews, screenshots, PTY  │
│ host ports: replaceable by embedding harness    │
│ packaging: standalone / bundle / MCP App        │
└─────────────────────────────────────────────────┘
        │
        ├── normal desktop/mobile browser
        ├── embedding host
        ├── MCP Apps host
        └── optional protocol adapters
```

The core API should be **capabilities, not widgets**. For example, a small TypeScript runtime surface conceptually resembling `host.storage`, `host.submit`, `host.events`, `host.identity`, `host.addressing` and `host.actions` is compatible with the commitments. A React component library can provide beautiful defaults for surveys, review panes, charts, presentation chrome and terminal frames, but every component should be replaceable by arbitrary code.

That is materially different from A2UI. A2UI intentionally represents UI through a declarative component contract and avoids arbitrary code; its extensibility comes from host-registered catalogs. citeturn19search0turn19search18turn2search26 Those are good properties when the host wants to render an untrusted agent’s intent natively on several platforms, but they defeat the explicit requirement that the coding agent may build any React application it can express.

It is also different from MCP Apps. MCP Apps deliberately puts the application in a sandboxed iframe and standardizes its communication with the host. citeturn21view3 That is a superb **distribution envelope**, but forcing all standalone artifacts through an iframe/tool/resource mental model would impose the needs of conversational MCP hosts on the local standalone runtime.

### Preserve freedom while separating trust

The “maximum capability” commitment does not require collapsing the trusted-host and artifact boundaries. In fact, MCP Apps provides useful prior art here: arbitrary app code can coexist with an explicit bridge and sandbox boundary. citeturn21view3 The standalone runtime should therefore distinguish:

**Artifact-authored application code** may implement arbitrary network calls, backend actions and UI. **Host-trusted controls**—for example a definitive “Submit to agent,” host identity indicator or permission/tunnel status—can live in host-rendered chrome outside the artifact DOM. This prevents an artifact from impersonating the authoritative host UI without imposing policy on what the artifact itself is allowed to display.

For local hygiene, the important defenses are protocol-level rather than content-level: loopback binding by default; session-scoped capability tokens; strict `Origin`/`Host` validation; CSRF protection on mutating server routes; authenticated WebSocket/SSE channels; explicit tunnel pairing; and no trust merely because a request reaches `localhost`. Those measures preserve the “curl-like” capability philosophy while addressing the stated concern that arbitrary third-party websites must not be able to drive a user’s local artifact process.

## Interoperability strategy

MCP Apps should be treated as the primary outward compatibility target. The standard now has the strongest combination of arbitrary HTML freedom, multiple-host distribution and alignment with the toolkit’s React/code-first model. Its official SDK explicitly serves app developers, host developers and MCP server authors; it provides React hooks and an App Bridge, while leaving hosts free to implement their own embedding layer. citeturn21view3

| Priority | Integration | Concrete shape | Estimated engineering cost | Why / what could change the priority |
|---|---|---|---|---|
| **Highest** | **Export/run an artifact as an MCP App** | Build the React artifact to browser assets; expose it as a `ui://` resource from an MCP server; map backend artifact actions to MCP tools; map artifact→host calls through App Bridge/PostMessageTransport; map host context into the toolkit identity/events ports. citeturn21view3 | **Medium** | Gives one artifact access to Claude, ChatGPT and other compliant hosts without changing its source model. | **Very high** | **Expose the toolkit itself as an MCP server/control plane** | In addition to the CLI/process API, offer tools such as create/open/build/inspect/screenshot/list-errors/submit-test-data. Val Town and MCP Apps’ own Agent Skills show the value of letting coding agents manipulate projects through standardized agent tooling. citeturn6search10turn21view3 | **Small–Medium** | Especially attractive for hosts other than the known Rust harness. Could remain optional if spawning the CLI is significantly more reliable for coding agents. |
| **High, but adapter-level** | **AG-UI bridge** | Map run lifecycle, state deltas, user actions and interrupts onto the toolkit’s event/submission ports. | **Optional** | **Render third-party MCP Apps inside the toolkit** | Implement the MCP Apps host/App Bridge side so an artifact can embed another tool’s `ui://` application. citeturn21view3 | **Medium–Large** | Valuable for composability, but less important than exporting this toolkit’s own artifacts. A crucial consequence is that **there should be no universal “UI protocol” inside the toolkit**. The ordinary React tree is the UI. Host interactions are typed service calls/events. An MCP Apps adapter serializes what MCP Apps needs; an AG-UI adapter emits AG-UI events; an A2UI surface can render A2UI. That preserves capability rather than choosing the least-common denominator.

There is also no need for special first-party interoperability with AI SDK or assistant-ui at the runtime level. Both are ordinary web packages designed to be used from application code. AI SDK is provider-agnostic and supports React plus other frameworks; assistant-ui exposes React primitives/runtimes. citeturn14search7turn4search2 The most powerful compatibility story is simply: **`npm install` them inside an artifact**.

## Adoption playbook and design ideas to borrow

### Patterns that actually spread developer tools

**Make ownership obvious.** shadcn/ui's defining idea is “open code”: components are brought into the application rather than hidden behind an opaque runtime, and its registry model has expanded to public and private registries. Its tooling now explicitly provides documentation/context to coding agents. citeturn12search17turn12search1turn12search5turn12search9 That maps unusually well to LLM authors: generated artifact code should be boring, inspectable and editable after the toolkit leaves the picture.

**Minimize the first command, then leave escape hatches everywhere.** Vite's adoption model combines one-command project creation and fast development with a plugin architecture rather than inventing an application framework; by 2026 Vite 8 was current, with more than 1,200 contributors and vendor-agnostic stewardship under an MIT license. citeturn12search2turn12search6turn12search14 Streamlit achieved the same psychological effect from another direction: a Python script becomes a working browser app with almost no ceremony. citeturn16search5

**Write documentation for agents as a primary audience, not as an afterthought.** MCP Apps now ships four Agent Skills directly in its repository; Shiny ships agent-readable skills with the package; shadcn has a command designed to provide documentation/code/examples as agent context; marimo has built adjacent tooling specifically for dropping agents into notebook sessions. citeturn21view3turn17search2turn12search9turn16search6 For this project, an agent skill may be as important as a human tutorial.

**Show source beside the spectacle.** Observable’s examples explicitly separate small reusable “techniques” from full “showcases,” encouraging users to inspect and copy source. citeturn15search5 A gallery for this toolkit should do both: tiny canonical patterns for agents to imitate and visually astonishing full artifacts that make humans want the tool.

**A memorable domain mapping beats a generic “framework” pitch.** Slidev maps Markdown/code to presentations; Spectacle maps React to decks; Remotion maps React to video; tldraw and Excalidraw turn canvas interactions into a recognizable product category. citeturn18search0turn18search1turn12search31turn13search14 The proposed toolkit needs an equally legible category noun—**artifact runtime** is clearer than “agentic UI framework.”

**License is part of the growth model.** There is a meaningful contrast among current developer tools. Streamlit, Gradio, Marimo, A2UI and AI SDK use permissive Apache-2.0 licenses; MCP Apps, AG-UI, Evidence, Quarto, Spectacle and much of the React UI ecosystem use permissive MIT-style licensing. citeturn16search2turn15search1turn16search0turn14search14turn14search3turn14search8turn14search5turn17search0turn17search6turn18search1 By contrast, Remotion's current model is source-available with free use for individuals, nonprofits/evaluation and small for-profit companies under stated conditions, while larger companies need a commercial license; tldraw's SDK likewise requires commercial licensing for commercial production use and moved away from ordinary permissive OSS licensing. citeturn12search28turn12search25turn13search0turn13search15 For a project whose proposed identity begins with “open-source” and whose goal is infrastructure-level adoption, a source-available core would create unnecessary positioning friction.

**Recommendation:** license the core/runtime/host SDK under **Apache-2.0** unless there is a specific organizational reason to prefer MIT. Apache-2.0 remains permissive while making the patent grant explicit, a useful property for enterprise infrastructure. Keep templates/examples equally permissive and make it unambiguous that generated artifacts belong to their authors. This is a strategic recommendation, not legal advice.

| **Downloadable/self-contained result** | Open Intelligent UI can export generated interfaces as standalone HTML; Observable and static publishing tools similarly emphasize portable outputs. citeturn22view0turn15search2 | Where an artifact does not require server actions, provide static/self-contained export. Where it does, export a bundle containing browser assets plus the artifact server. |

The gallery should lead with capabilities that are **hard to mistake for existing chat UI libraries**. A generic weather card or stock chart would undersell the project because every generative-UI stack can now do those. Strong launch demos would instead include an AI-drafted inbox where the human edits a reply and the artifact’s authored backend action actually sends it; a pixel-faithful interactive terminal/TUI replay beside explanatory browser UI; a five-candidate design/code review with anchored comments and a structured final submission; a live operational dashboard changing via subscriptions while open; a polished presentation containing real live application demos; and the same artifact running standalone locally and then, unchanged at source level, inside an MCP Apps host.

For naming, avoid terminology that makes the project sound like another schema or chatbot library: “GenUI,” “agent UI,” “components,” and “canvas” are now crowded concepts. The strongest names will be **short, pronounceable, CLI-friendly nouns** where the product name, executable name and conceptual unit can match. The descriptive category can remain “agent artifact runtime” even if the eventual brand name is more distinctive.

The decisive product idea is that **an artifact is not a special UI format**. It is a small piece of agent-authored software whose runtime contract makes it safe to hand to a human and easy to reconnect to an agent.

That yields a differentiated promise:

> **Write normal React. Get a human-facing artifact with durable state, real actions, reviews, presentations, live data, exact terminal experiences, and a clean path back to the agent—locally, embedded in any host, or packaged for MCP Apps.**

The 2026 landscape strongly supports the pieces of that architecture without yet collapsing them into one system. Claude validates durable interactive artifacts and AI-inside-artifact experiences; ChatGPT Intelligent UI validates dynamic, progressively rendered interfaces; Open Intelligent UI validates open generated code; Replit validates multi-artifact projects; Streamlit and marimo validate extreme authoring speed; MCP Apps validates portable arbitrary web UI; AG-UI validates a protocol boundary for human/agent interaction; and A2UI validates the importance of explicit state/action boundaries even where its declarative representation is not appropriate here. citeturn1search2turn21view0turn22view0turn6search22turn16search5turn16search4turn21view3turn19search23turn21view2

The opportunity is therefore not to invent yet another way for a model to specify a button. It is to make **ordinary agent-written software a first-class, inspectable, durable, embeddable medium of communication between agents and humans**.
